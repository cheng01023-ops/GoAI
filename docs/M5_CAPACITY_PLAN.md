# M5 16GB 上榨干 CPU+GPU 的可行性与路线（实测基线）

> 本文件由一次实测会话生成：所有数字都是**这台 M5 / 16GB 上当场跑出来的**，
> 不是估算。用来回答一个问题：**在这台机器上开发围棋 AI 并本地训练，
> 怎么让 CPU 和 GPU 都吃满，以及吃满之后能换来什么。**

## 一、硬件事实（实测）

| 项 | 实测值 | 备注 |
|---|---|---|
| 芯片 | Apple M5 | 10 核 GPU（Metal 3/4），CPU 4 性能核 + 6 能效核 |
| 统一内存 | 16 GiB（17179869184 B） | CPU/GPU 共享同一块 |
| **GPU 可用内存上限** | **11.84 GB**（recommendedMaxWorkingSetSize） | 不是 16GB，训练 batch 要按这个算 |
| 单缓冲上限 | 8.88 GB（maxBufferLength） | |
| 磁盘 | 926 GB 卷，已用 158 GB，可用 **741 GB** | |
| macOS | 26.6.2，Python 3.14.7 | torch 2.14.1 有 cp314 arm64 wheel（含 MPS） |
| 编译链 | clang / make / git 已装；**无 cmake、无 brew** | GoAI 不用 cmake，无影响 |

关键：**MPS 后端最多给你 ~11.8 GB**。别的进程已占 2~3 GB 时，
真正能喂给 GPU 的 batch/模型只剩 ~8 GB 量级 —— 这是本机做 GPU 训练的硬天花板。

## 二、CPU 侧的实测极限（本次新增测量）

同一网络（9 路 32 通道 2 残差块，29K 参数）、同样 400 模拟、每轮 40 局，
只改 `--threads`：

| threads | 自对弈耗时 | 墙钟 | sims/s | 相对 1 线程加速 | 并行效率 |
|---|---|---|---|---|---|
| 1 | 132.3 s | 132 s | 11 090 | 1.00× | — |
| 4 | 46.1 s | 46 s | **32 600** | **2.87×** | 72% |
| 10 | 29.0 s | 29 s | **51 700** | **4.57×** | **46%** |

（sims/s = 局面数 × 400 / 自对弈秒数。局面数：3670 / 3775 / 3750）

**结论（重要）**：
- 从 4 线程加到 10 线程，多出的 6 个**能效核只贡献了 1.6×**，并行效率从 72% 掉到 46%。
  → 自对弈线程数用 **4~6** 就够；再加线程主要在浪费电和加剧内存带宽争抢。
- 与项目早期 8 通道网络 bench（39 538 evals/s，单线程）对照：32 通道单线程只有 11 090 sims/s，
  **约 3.2× 慢**，和卷积工作量 4× 相称 → **时间确实花在网络前向上**，瓶颈确认。

## 三、把瓶颈换算成绝对算力

- 现网络算力需求：9 路 32ch×2blk ≈ **6.5 MFLOP/局面**
- 实测 10 线程 51 700 sims/s ≈ 51 700 evals/s → **≈ 0.34 GFLOP/s 有效算力**
- 即：**CPU 上这台 M5 对该网络的有效吞吐约 5 万 evals/s 量级，且已接近并行效率上限**

同一瓶径下要 5 000 模拟/手，需要的吞吐：

| 模拟/手 | 需要 evals/s | 相当于现在（≈5万/s）的倍数 |
|---|---|---|
| 800（现状） | ≈70 000 | 1.4×（勉强） |
| 2 000 | 173 000 | 3.5× |
| 5 000 | 434 000 | **8.7×** |

→ **想靠搜索深度换棋力，CPU 这边最多再挖 1.4×，必须换硬件路径（GPU）或者换网络规模。**
这正好解释了项目里"800 模拟 + 29K 参数已到平台"的观察：不是训练方法问题，是吞吐上限。

## 四、GPU 侧的现状

- **训练阶段只占每轮 2%（4.5s / 294s）→ 把"训练"搬到 GPU 收益上限只有 2%。**
  这是本项目最容易走偏的一点：优化梯度训练没有意义。
- 自对弈（75%）和评估（23%）**完全跑在 CPU 上，GPU 全程闲置**。
- 所以"榨干 GPU"的正确定义是：**把叶子评估（推理）搬到 GPU，让 GPU 吃推理、
  CPU 只吃树操作**，而不是把训练搬过去。
- 已有基础设施：`search_select_leaf / search_apply_leaf` 两阶段批量接口、
  `gpu/server.py` 批量推理服务、`gtrain`（C 搜索 + GPU 批量）子命令 —— 都是为这条路准备的。

### GPU 能否赢的关键量：切换点

- 单点送 GPU 一定更慢：M5 上一次前向 0.025~0.1 ms，而一次 Metal/MPS kernel 启动开销就 0.05~0.1 ms 量级。
- GPU 只有在**批量摊薄启动开销**后才赢。经验判据：**batch ≥ 32~64** 才看到净收益。
- GPU 批量还顺带解决"评估也要算力"的问题（可把评估也批量送到同一服务）。

### 待补测（torch 正在装，装完即可跑）

分别测**纯推理**与**训练(fwd+bwd)**，输出 samples/s 与 μs/sample。
拿到那条曲线后三个问题一次回答完：
1. MPS 的 batch 吞吐能否超过 CPU 的 5 万/s？
2. 最优 batch 是多大（受 11.8 GB 上限约束）？
3. 网络放大到 64/128 通道后，GPU 方案还剩多少余量？

预估（需实测确认）：网络放大到 **64ch×4blk ≈ 49 MFLOP/局面（7.5×）**、
或 **128ch×6blk ≈ 289 MFLOP/局面（44×）** 时，CPU 直接崩（11 090 / 7.5 ≈ 1 500 evals/s），
而 GPU 批量仍能保持每秒上万到十几万局面 → **大网络只能在 GPU 上训，这是分水岭。**

## 五、推荐路线（按收益排序，每步都有验收判据）

### 第 1 步：跑 MPS 批量基准，画 batch-吞吐曲线（半天）
- 验收：得到 μs/sample vs batch 曲线；找到 GPU 吞吐 ≥ 5 万/s 的最小 batch。
- 若曲线显示 GPU 在任意 batch 都赢不了 CPU → 立刻停止 GPU 方向，转第 5 步。

### 第 2 步：把 MCTS 叶子评估改成批量（1~2 天）
- 先做 **CPU 批量版**并验证"批量结果与单点结果逐值一致"（沿用项目既有对拍规范）。
- 再切 GPU 后端（`gpu/server.py` 已有 socket 协议，加 batch 接口）。
- 验收：**搜索吞吐 ≥ 3× 现状**（且锚点胜率不降）。达不到 3× 就回滚，不改架构。

### 第 3 步：用省下的算力换搜索深度（持续实验）
- 800 → 2 000 → 5 000 模拟，锚点判定。
- 依据项目已有规律（模拟 140→800 让锚点从退化变 70%），这一步是**当前最大的棋力杠杆**。
- 验收：成对开局锚点胜率显著上升（对照 ±95% 置信区间）。

### 第 4 步：加容量（配合第 3 步，一起做才划算）
- 32ch → 64ch×4blk → 128ch×6blk，配 `tools/warm_start.py` 热启动。
- 前向成本涨 7.5× / 44×，**必须已经有 GPU 批量**才动这一步。
- 验收：同搜索预算下锚点高于小网络。

### 第 5 步（真正的"榨干 CPU+GPU"）：让两条流水线并行
当前是**串行**的：自对弈（CPU 忙、GPU 闲）→ 训练（GPU 忙、CPU 闲）。
改成并行后：
- CPU 进程：自对弈 MCTS 搜索（4~6 线程，别用满 10）
- CPU/GPU：推理服务（批量）跑在 MPS 上
- 训练进程：同一服务里做梯度更新，用 `torch.mps` 的独立 stream
- 关键：**推理 batch 和训练 batch 复用同一份权重副本**，避免两份模型挤爆 16 GB
- 内存约束：`torch.mps.set_per_process_memory_fraction(0.6~0.7)`；
  推理 batch ≤ 256；训练 batch ≤ 512（9 路小网络实测够用）
- 验收：同一墙钟时间内**(新增自对弈局面数 + 完成的训练步数) 同时提升**，
  且 `ps` 中 CPU 占用 ≥ 400%、GPU 侧有持续负载。

## 六、本机专属的坑（必须记住）

1. **GPU 上限是 11.84 GB，不是 16 GB。** batch 按 8 GB 预算设计。
2. **MPS 与高性能 CPU 自对弈同时满载会互相抢**（统一内存带宽 + 功耗预算）。
   实测 4→10 线程只剩 46% 效率，说明带宽已经紧张；
   开 GPU 时自对弈线程降到 4，反而整体更快（需 A/B 验证后固定）。
3. **系统内存本来就紧**（当前 swap 已用 3.96 GB / 5 GB，压缩器占用 3.3 GB）。
   跑大 batch 前先看 `vm_stat` / `sysctl vm.swapusage`，swap 飙升就减小 batch。
4. **不要在 16 GB 上跑 19 路 128ch 的网络**；9 路是这台机器的甜点。
5. 项目规范继续生效：A/B 必须独占机器 + 交替测量；判据是成对开局锚点，不是损失。

## 七、一句话总结

> 在这台 M5/16GB 上，"榨干 GPU" 不等于"用 GPU 训练"（训练只占 2%），
> 而是**把自对弈的叶子评估批量搬到 GPU**，把省下的时间换成**更深的搜索 + 更大的网络**。
> CPU 侧已经接近极限（4 线程 2.87×，10 线程只有 4.57×），再堆线程无效。
> 顺序必须是：先批量（第 2 步）→ 再深度（第 3 步）→ 最后容量（第 4 步）；
> 反过来做只会得到一个又慢又弱的网络。
